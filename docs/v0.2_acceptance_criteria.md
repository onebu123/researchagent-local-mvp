# ResearchAgent v0.2 验收标准

生成日期：2026-06-05

适用范围：基于 ResearchAgent v0.1 现有 FastAPI + SQLite + 本地文件存储 + Next.js dashboard + 轻量串行 Agent workflow 演进。v0.2 不大改架构，不引入生产级多租户、复杂编排或炫技功能，重点把系统从“可运行 demo”提升到“初步可信科研草稿系统”。

## 1. v0.2 目标

v0.2 的目标是补齐科研可信链路的最低门槛：

1. PDF 不再只是保存文件，至少能抽取文本、记录解析状态和解析 provenance。
2. 文献不再只是 placeholder 摘要，至少有可核验的 metadata、source_id 和引用状态。
3. Manuscript 中的关键 claim 不再只有单条模板，必须能追溯到数据、图表、文献或明确标记为待核验。
4. Reviewer 不只检查是否有 Evidence Checklist，还要检查引用、claim、图表、placeholder、过度表述和待人工核验项。
5. 前端不只显示最新输出列表，还要能打开 Output/Evidence 详情，帮助用户看到“这句话凭什么成立”。
6. v0.2 验证脚本必须能自动检查 PDF、metadata、evidence、review、frontend build 和核心 API 的最低可信标准。

v0.2 验收结论只能分为：

- `pass`：满足本文件全部必选项。
- `partial`：主流程可跑通，但有明确验收项缺失。
- `fail`：workflow 无法完成、关键文件缺失、伪造引用/结果、或 evidence 无法追溯。

## 2. 必须实现的功能

### 2.1 PDF 解析与文献输入

1. 文献上传后仍保存原始文件到 `projects/{project_id}/literature/`。
2. PDF 必须被解析成项目内文本产物，例如 `literature/parsed/{source_id}.txt`。
3. 每个 PDF 必须生成解析记录，例如 `literature/parsed/{source_id}.json` 或统一的 `literature/sources.json`。
4. 解析记录必须包含：`source_id`、原文件名、相对路径、文件类型、解析状态、文本长度、页数或页数未知原因、解析工具、解析时间、错误信息。
5. TXT/Markdown 文献也必须进入同一套 source registry，不再只作为匿名文本拼接。
6. Literature Agent 必须读取 source registry，而不是只读目录文本。

### 2.2 文献元数据与引用

1. 必须新增文献元数据文件，例如 `literature/sources.json`。
2. 每条文献必须有稳定 `source_id`，如 `S001`、`S002`。
3. 每条 metadata 必须包含字段：`source_id`、`type`、`title`、`authors`、`year`、`venue`、`doi`、`url`、`file_path`、`parsed_text_path`、`verification_status`、`notes`。
4. 缺失字段必须显式写 `null` 或空数组，并将 `verification_status` 标为 `missing_metadata` 或 `needs_manual_review`。
5. 系统不得自动补造 DOI、作者、年份、期刊、页码、出版社或引用关系。
6. Manuscript 的 References 不得再只有 “No verified references in v0.1”；必须输出真实 source registry 中的条目，并标记核验状态。

### 2.3 Evidence claim 扩展

1. `provenance/evidence.json` 必须从单条模板扩展为多条 claim。
2. 每条 claim 必须绑定章节、claim 文本、证据类型、证据来源和核验状态。
3. Evidence 必须同时支持以下来源类型：
   - `analysis`：来自 `analysis/result_summary.json`。
   - `figure`：来自 `figures/figure_provenance.json`。
   - `literature`：来自 `literature/sources.json` 或解析文本。
   - `manual_required`：系统识别出必须人工补证据的 claim。
4. Manuscript 中 Results 相关 claim 必须绑定 analysis 或 figure。
5. Introduction/Discussion 中引用文献的 claim 必须绑定 literature source_id，或标为 `needs_manual_review`。
6. 任何 claim 如果无法找到证据，不得静默通过；必须进入 Reviewer major issue 或 warning。

### 2.4 Reviewer 增强

1. Reviewer 必须读取 manuscript、sources、evidence、figure provenance 和 analysis summary。
2. Reviewer 报告必须输出 JSON 和 Markdown。
3. JSON 必须包含：`overall_decision`、`major_issues`、`minor_issues`、`missing_evidence`、`citation_issues`、`overclaims`、`placeholder_issues`、`figure_issues`、`metadata_issues`、`human_review_required`、`suggested_revisions`。
4. Reviewer 必须把“缺少文献元数据”“claim 无证据”“placeholder 进入正式段落”“引用状态待核验”“Results 超出 analysis/figures”列为可检测问题。
5. Reviewer 不得因为 workflow 能跑通就给通过结论；证据不足时必须给 `major_revision` 或更严格结论。

### 2.5 前端详情页

1. 在不大改前端架构的前提下，增加 Output 详情页或详情视图。
2. 增加 Evidence 详情页或详情视图。
3. 用户必须能从 dashboard 最新输出进入详情。
4. 详情页必须展示内容、相对路径、mime type、Agent、创建时间和 evidence/citation 状态。
5. 二进制输出如 PNG 不必直接内嵌完整读取，但必须清楚显示文件信息和不可文本预览原因。

### 2.6 Demo 与脚本

1. `scripts/seed_demo.py` 必须生成至少 1 个可解析 demo PDF 或用于 PDF 解析测试的最小 PDF fixture。
2. demo 必须包含至少 2 条文献 source，其中至少 1 条 metadata 不完整，用于验证 `needs_manual_review`。
3. demo workflow 完成后必须生成 PDF 解析产物、source registry、扩展 evidence、增强 reviewer 报告和前端可读取的 output 列表。
4. 新增 `scripts/validate_v02.py`，作为 v0.2 自动验收入口。

## 3. 不做的功能

v0.2 明确不做以下功能，避免范围膨胀：

1. 不替换为 PostgreSQL，不做数据库迁移体系。
2. 不引入用户登录、RBAC、多租户权限和项目成员体系。
3. 不引入 LangGraph 或生产级任务队列。
4. 不做真实联网文献检索、学术数据库接入或自动 DOI 查询。
5. 不做完整引用格式引擎，不要求 APA/GB/T 7714 全量格式正确。
6. 不做统计显著性检验、p 值、因果推断或模型评估。
7. 不做真实 LLM eval 平台，不要求接入真实 OpenAI-compatible API。
8. 不做生产部署、云存储、对象存储、CDN、可观测性和告警。
9. 不做病毒扫描或 PDF 沙箱隔离的生产级能力；但必须有文件大小、类型和解析失败边界。
10. 不做完整论文生成器；系统仍必须明确“不是论文代写器”。
11. 不隐藏 AI 使用，不提供降重、绕过查重或绕过 AI 检测能力。

## 4. PDF 解析验收标准

### 4.1 成功解析标准

给定 demo PDF 上传或 seed 后运行 workflow，必须满足：

1. 原始 PDF 存在于 `literature/` 下。
2. 解析文本产物存在，路径登记在 source registry。
3. 解析文本长度大于 100 个字符。
4. 解析记录包含 `parse_status="parsed"`。
5. 解析记录包含 `parser_name` 和 `parsed_at`。
6. 解析记录包含 `page_count`；如果工具无法获取页数，必须写 `page_count=null` 和 `page_count_note`。
7. Literature Agent 的综述必须引用该 PDF 的 `source_id`。

### 4.2 失败解析标准

给定损坏 PDF 或无法解析 PDF，系统必须：

1. 不让 workflow 崩溃。
2. 保留原始文件。
3. 生成解析记录，`parse_status` 为 `failed` 或 `needs_manual_review`。
4. 记录可读错误摘要，但不泄露内部堆栈或绝对路径。
5. Reviewer 必须把该 source 加入 `metadata_issues` 或 `human_review_required`。

### 4.3 安全与边界标准

1. PDF 上传仍必须限制在项目目录内。
2. 必须限制上传文件大小；默认上限可先定为 10MB。
3. PDF 解析不得写出项目目录。
4. 文件名必须继续使用现有 `safe_filename` 类似策略。
5. v0.2 不要求病毒扫描，但文档和 Reviewer 必须提示 PDF 解析结果需要人工核验。

## 5. 文献元数据和引用验收标准

### 5.1 Source Registry

`literature/sources.json` 必须是数组，每条记录至少包含：

```json
{
  "source_id": "S001",
  "type": "pdf",
  "title": "待核验标题",
  "authors": [],
  "year": null,
  "venue": null,
  "doi": null,
  "url": null,
  "file_path": "literature/example.pdf",
  "parsed_text_path": "literature/parsed/S001.txt",
  "verification_status": "needs_manual_review",
  "notes": []
}
```

验收要求：

1. `source_id` 必须唯一且稳定。
2. `file_path` 和 `parsed_text_path` 必须是项目内相对路径。
3. `verification_status` 只允许使用约定枚举：`verified`、`needs_manual_review`、`missing_metadata`、`parse_failed`。
4. demo 中不得把 placeholder 文献标为 `verified`。
5. 缺少 DOI 不算失败，但必须明确标为待核验。

### 5.2 引用生成

1. Manuscript 的 References 必须来自 `sources.json`。
2. 每条引用必须显示 `source_id` 和 `verification_status`。
3. 正文中引用文献时必须使用可追踪占位，例如 `[S001, needs_manual_review]`。
4. Literature Review 中的关键观点必须能追溯到至少一个 source_id。
5. 系统不得自动制造不存在的页码、作者、DOI、期刊或年份。

## 6. Evidence claim 扩展验收标准

`provenance/evidence.json` 必须包含不少于 3 条 claim，且至少覆盖：

1. 一条 Results claim，证据类型为 `analysis`。
2. 一条 Figure claim，证据类型为 `figure`。
3. 一条 Literature claim 或 `manual_required` claim。

每条 claim 必须包含：

```json
{
  "claim_id": "claim_001",
  "section": "Results",
  "claim": "当前结果仅报告 CSV 数据的描述性统计。",
  "evidence_type": "analysis",
  "evidence_refs": [
    {
      "kind": "analysis",
      "path": "analysis/result_summary.json",
      "field": "row_count"
    }
  ],
  "source_ids": [],
  "figure_ids": [],
  "verification_status": "machine_checked",
  "human_verified": false,
  "limitations": ["不包含 p 值或因果结论"]
}
```

验收要求：

1. `claim_id` 唯一。
2. `section` 必须对应 manuscript 中存在的章节。
3. `evidence_refs` 不得为空，除非 `evidence_type="manual_required"`。
4. `analysis` claim 必须引用存在的 analysis 文件。
5. `figure` claim 必须引用存在的 figure id 和 figure 文件。
6. `literature` claim 必须引用存在的 source_id。
7. `verification_status` 允许：`machine_checked`、`needs_manual_review`、`unsupported`。
8. `human_verified` 默认为 `false`，不得自动写 `true`。
9. Unsupported claim 必须进入 Reviewer 的 `missing_evidence`。

## 7. Reviewer 增强验收标准

Reviewer v0.2 必须检查以下内容：

1. Manuscript 是否包含 References 和 Evidence Checklist。
2. References 是否来自 `literature/sources.json`。
3. 正文 source_id 是否都存在于 sources。
4. `verified` 以外的引用是否被标注待核验。
5. `evidence.json` 是否不少于 3 条 claim。
6. 每条 claim 是否有有效 evidence_refs 或明确 `manual_required`。
7. Results 是否只使用 `analysis_results` 和 `figures`。
8. 图表是否都有 `figure_provenance.json` 记录。
9. 图表是否均 `is_ai_generated=false`。
10. Manuscript 是否含有未限定的“证明”“证实”“显著提高”“因果”等过度表述。
11. demo、mock、placeholder 是否进入正式结论但未披露。
12. PDF 解析失败或 metadata 缺失是否被列为人工核验项。

Reviewer JSON 必须满足：

1. `overall_decision` 只能是：`accept_with_notes`、`minor_revision`、`major_revision`、`reject_for_missing_evidence`。
2. 只要存在 unsupported claim，必须为 `major_revision` 或 `reject_for_missing_evidence`。
3. 只要所有文献都是 `needs_manual_review`，不得给 `accept_with_notes`。
4. `human_review_required` 必须列出需要作者人工确认的 source_id、claim_id 或 output path。

## 8. 前端 Evidence/Output 详情页验收标准

### 8.1 Output 详情

前端必须提供 Output 详情页或详情视图，建议路径：

- `/projects/{project_id}/outputs/{output_id}`，或
- dashboard 内部可分享/可返回的详情面板。

验收要求：

1. 从 `RecentOutputs` 可进入详情。
2. 详情页调用 `GET /api/projects/{project_id}/outputs/{output_id}`。
3. 显示标题、Agent、kind、mime type、relative path、created_at。
4. JSON 输出用格式化 JSON 展示。
5. Markdown/TXT/CSV/SVG 以文本或预览形式展示。
6. PNG 等 binary 输出显示文件信息和“当前 API 不返回二进制内容”的提示。
7. 加载失败时显示可恢复错误，不空白。

### 8.2 Evidence 详情

前端必须提供 Evidence 详情页或详情视图，最低要求：

1. 能展示 `provenance/evidence.json` 中每条 claim。
2. 每条 claim 显示 `claim_id`、section、claim 文本、evidence_type、verification_status、human_verified。
3. evidence_refs/source_ids/figure_ids 以可读列表展示。
4. unsupported 或 needs_manual_review 有明显状态标记。
5. 用户能从 Evidence 详情返回 dashboard。

### 8.3 不要求

1. 不要求在线编辑 evidence。
2. 不要求图表交互缩放。
3. 不要求下载文件。
4. 不要求复杂路由权限。

## 9. 新增测试要求

### 9.1 后端测试

必须新增或扩展 pytest：

1. PDF 解析成功：上传/seed PDF 后生成 parsed text 和 source registry。
2. PDF 解析失败：损坏 PDF 不导致 workflow 崩溃，source 标记失败。
3. Source registry：source_id 唯一，必需字段存在，相对路径不越界。
4. 引用安全：缺 DOI/作者/年份时标记待核验，不自动补造。
5. Evidence schema：不少于 3 条 claim，字段完整，路径存在。
6. Unsupported claim：Reviewer 必须报告 missing evidence。
7. Figure provenance：图表仍为 `is_ai_generated=false`。
8. Output detail API：JSON/Markdown/CSV/SVG/binary 输出读取语义正确。
9. 上传边界：非法后缀、超大文件、路径穿越文件名均被拒绝或安全处理。
10. 回归：`validate_v01.py` 仍应通过或 v0.2 validation 覆盖 v0.1 所有核心断言。

### 9.2 前端测试

最低要求：

1. `npm run typecheck` 通过。
2. `npm run build` 通过。
3. 如引入 Playwright，至少覆盖：
   - dashboard 加载 demo project。
   - 从 RecentOutputs 打开 Output 详情。
   - 打开 Evidence 详情并看到 claim 列表。
   - 后端错误时显示错误态。

不强制要求视觉回归和跨浏览器矩阵。

### 9.3 验证脚本

必须新增 `scripts/validate_v02.py`，作为 v0.2 的单命令验收入口。

脚本必须：

1. 使用 FastAPI TestClient 或项目服务层，不依赖公网。
2. 使用独立 demo/fixture，避免污染用户真实项目。
3. 输出清晰失败信息。
4. 成功时打印 `ResearchAgent v0.2 validation passed.`。

## 10. `validate_v02.py` 应该检查哪些内容

`scripts/validate_v02.py` 至少检查以下项目：

### 10.1 基础 API 与项目

1. `GET /health` 返回 200 且 `status=ok`。
2. 可以创建或覆盖 v0.2 demo project。
3. `GET /api/projects/{project_id}` 返回资源统计和 latest_outputs。

### 10.2 PDF 与 sources

1. demo project 中至少存在 1 个 PDF source。
2. PDF source 有原始文件、解析文本和解析记录。
3. 解析文本长度大于 100。
4. `literature/sources.json` 存在且至少 2 条 source。
5. 所有 source_id 唯一。
6. 每条 source 包含必需 metadata 字段。
7. 至少 1 条 source 为 `needs_manual_review` 或 `missing_metadata`。
8. 没有 source 被错误标记为 verified，除非测试 fixture 明确提供完整 metadata。

### 10.3 Workflow 输出

1. `POST /api/projects/{project_id}/workflow/run` 返回 200。
2. `workflow_status=completed`。
3. 必需文件存在：
   - `literature/sources.json`
   - `literature/literature_review.md`
   - `analysis/result_summary.json`
   - `figures/figure_provenance.json`
   - `manuscript/draft.md`
   - `manuscript/refined.md`
   - `reviews/review_report.json`
   - `reviews/review_report.md`
   - `provenance/evidence.json`
4. SQLite outputs 中登记上述关键输出。

### 10.4 Manuscript 与引用

1. `draft.md` 包含 References。
2. References 中包含 source_id。
3. `draft.md` 包含 Evidence Checklist。
4. `draft.md` 不包含伪造 DOI 样式字段，除非 source registry 中真实提供。
5. demo/placeholder 内容必须被披露。

### 10.5 Evidence

1. `evidence.json` 至少 3 条 claim。
2. claim_id 唯一。
3. 每条 claim 包含：`claim_id`、`section`、`claim`、`evidence_type`、`verification_status`、`human_verified`。
4. 至少 1 条 `analysis` claim。
5. 至少 1 条 `figure` claim。
6. 至少 1 条 `literature` 或 `manual_required` claim。
7. analysis/figure/literature claim 的引用路径或 id 必须存在。
8. `human_verified` 不得自动为 true。

### 10.6 Reviewer

1. `review_report.json` 包含 v0.2 必需字段。
2. `overall_decision` 属于允许枚举。
3. metadata 不完整时，Reviewer 报告 human_review_required。
4. unsupported claim 存在时，Reviewer 不得给 `accept_with_notes`。
5. overclaims 字段存在，即使为空数组。
6. citation_issues、metadata_issues、missing_evidence 字段存在。

### 10.7 Output/Evidence API

1. `GET /api/projects/{project_id}/outputs` 返回非空。
2. 能通过 output_id 读取 `evidence.json` 输出。
3. JSON 输出返回 dict/list content。
4. Markdown 输出返回字符串 content。
5. PNG 输出返回 `binary=true` 且 `content=null`。

### 10.8 回归检查

1. `figure_provenance.json` 所有图表 `is_ai_generated=false`。
2. `analysis/result_summary.json` 仍包含 row_count、column_count、numeric_columns。
3. workflow 不生成 p 值字段，除非未来有真实统计模块和明确人工确认。
4. LLM API key 为空时仍能在 mock 模式跑通。

## 验收通过定义

v0.2 只有在以下条件同时成立时才算通过：

1. `python scripts/validate_v02.py` 输出 `ResearchAgent v0.2 validation passed.`。
2. `python -m pytest services/api/tests` 通过。
3. `npm run typecheck` 通过。
4. `npm run build` 通过。
5. `npm audit` 无高危或严重漏洞；如果有非阻断漏洞，必须在报告中说明来源和暂不处理原因。
6. v0.1 的核心能力没有回退：创建项目、上传文献/CSV、完整 workflow、分析、图表、论文、Reviewer、evidence 输出仍可用。

## 技能使用与边界说明

- must：`academic-writing`、`test-engineering`。用于定义科研诚信、引用核验、claim 证据链和验证脚本门禁。
- conditional：`web-security`、`code-audit`、`api-engineering`、`backend-engineering`、`nextdev`、`react-development`。本次未读取 raw；文档中只提出 PDF/上传/前端详情的验收边界，不实施代码修改。
- 本文档仅基于当前 v0.1 项目文件和本地文档生成，未使用外部资料调研。
