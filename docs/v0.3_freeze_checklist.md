## 2. v0.3 已完成能力

### 2.1 Post-Manuscript Claim Alignment

- 新增 Claim Alignment Agent。
- Manuscript Agent 生成 `draft.md` 后，系统会扫描 Results / Discussion 关键句。
- 每个句子标记为：
  - `matched`
  - `needs_claim_alignment`
  - `not_claim`
- 输出：
  - `projects/demo_project/provenance/claim_alignment.json`

### 2.2 Reviewer Sentence-Level Issue

- Reviewer 不再只输出全局问题。
- `review_report.json` 新增 `sentence_issues`。
- 每条 issue 可定位到：
  - section
  - paragraph_index
  - sentence_index
  - sentence
  - issue_type
  - severity
  - related_claim_id
  - suggested_revision
- Reviewer 可识别 claim alignment 缺口和强结论词 overclaim。

### 2.3 Literature Metadata Editor

- 新增文献 metadata 读取和 PATCH API。
- 前端可查看和编辑：
  - title
  - authors
  - year
  - doi
  - journal
  - metadata_status
  - human_verified
- 只有 `metadata_status=verified` 且 `human_verified=true` 的文献可进入 `Verified references`。
- 系统不会自动伪造 DOI、作者、年份或期刊。

### 2.4 PDF Parse Quality Report

- PDF metadata 新增质量字段：
  - text_length
  - empty_page_count
  - extraction_method
  - warning_count
  - quality_score
  - quality_label
  - needs_manual_review
- Literature Agent 会在文献综述中提示 PDF 解析质量风险。
- Reviewer 会将低质量 PDF 解析风险写入 metadata 或 citation 相关 issue。

### 2.5 Analysis Provenance

- Analysis Agent 新增输出：
  - `analysis/analysis_provenance.json`
- 记录：
  - input_data_file
  - input_data_hash
  - analysis_function
  - generated_files
  - runtime
  - row_count
  - column_count
  - warnings
  - limitations
  - is_demo_data
- evidence analysis claim 绑定 `analysis/analysis_provenance.json`。

## 3. v0.3 与 v0.2 的主要差异

| 维度 | v0.2 | v0.3 |
| --- | --- | --- |
| Claim 对齐 | evidence 先于 manuscript 生成，未做正文句子级二次对齐 | manuscript 后新增 claim alignment，输出 `claim_alignment.json` |
| Reviewer 定位 | 全局 issue 为主 | 新增 `sentence_issues`，定位到句子 |
| 文献 metadata | 有 `literature_index.json`，但主要是结构字段 | 新增 GET/PATCH API 和前端 metadata editor |
| Verified references | 已区分 placeholder / verified | 强化为仅允许人工 verified 进入 Verified references |
| PDF metadata | 有 parse_status、char_count、warnings | 新增 quality_score、quality_label、needs_manual_review |
| Analysis 输出 | `result_summary.json` 为主 | 新增 `analysis_provenance.json` |
| Evidence claim | 至少 3 条 claim | analysis claim 绑定 analysis provenance |
| 前端详情 | Output/Evidence/Figure provenance drawer | 增加 Claim/Sentence/Literature/Analysis 四类面板 |
| API | evidence、figure provenance、outputs | 新增 claim alignment、analysis provenance、literature GET/PATCH、sentence issues |
| E2E | 无 Playwright E2E | 新增最小 Playwright mock fallback E2E |
| 验证脚本 | `validate_v01.py`、`validate_v02.py` | 新增 `validate_v03.py`，并保护 v0.1/v0.2 验证 |

## 8. v0.3 当前安全边界

### 8.1 文件路径边界

- 项目文件位于 `projects/{project_id}`。
- 上传和输出读取通过项目目录边界保护。
- 新增 API 读取项目 JSON 时继续使用项目路径保护。
- API 返回相对路径，不返回内部绝对路径作为业务字段。

### 8.2 文献引用边界

- placeholder 文献不得自动升级为 verified。
- 系统不自动生成 DOI、作者、年份、期刊或页码。
- Verified references 只来自 `metadata_status=verified` 且 `human_verified=true`。
- Literature Metadata Editor 只保存用户输入，不做联网核验和自动补全。

### 8.3 科研结论边界

- Manuscript Results 只能基于：
  - `analysis/result_summary.json`
  - `analysis/analysis_provenance.json`
  - `figures/figure_provenance.json`
  - `provenance/evidence.json`
- 不生成 p 值、统计显著性、因果结论或真实实验结论。
- Reviewer 会检查 strong conclusion terms 和缺失统计证据的 overclaim。

### 8.4 图表边界

- `figure_provenance.json` 必须保留：
  - `is_ai_generated=false`
  - `is_experimental_result=true`
  - `source_data`
  - `output_files`
  - `data_hash`
- source data 不存在时不得伪造图表。

### 8.5 PDF 解析边界

- PDF 解析失败不得删除原始 PDF。
- 解析失败、fallback 和低质量解析必须写入 metadata warnings 或 quality 字段。
- 低质量 PDF 解析结果不得作为可靠全文来源。

### 8.6 Mock / Demo 边界

- 无 API key 环境必须继续可运行 mock demo。
- 前端后端不可用时必须继续 mock fallback 渲染。
- mock、demo、placeholder 不得伪装成真实科研结论。

## 9. v0.3 已知限制

1. PDF 解析质量仍为基础规则评分，不支持复杂版面、扫描件 OCR、公式、表格和图片注释的高质量抽取。
2. PyMuPDF 不可用时 fallback 能力有限，只适合 demo 或简单 PDF。
3. Claim Alignment 是规则实现，不是语义级 LLM 对齐。
4. Reviewer 是规则检查器，不能替代人工学术审稿。
5. sentence issue 能定位问题句，但还没有生成精确 diff。
6. Literature Metadata Editor 不做变更历史、审计日志或批量校验。
7. Analysis Provenance 记录运行环境和数据 hash，但未记录分析参数、脚本版本、随机种子和依赖锁定。
8. Playwright E2E 当前覆盖 mock fallback，不覆盖真实后端 workflow 端到端。
9. 当前仍使用 SQLite 和本地文件系统，只适合本地 MVP。
10. 没有生产级队列、权限、审计日志、备份、监控、速率限制和安全加固。

## 10. v0.3 为什么仍不适合公网生产

v0.3 是本地可信草稿系统，不是公网生产系统。原因如下：

1. 没有用户认证、授权、项目成员权限和资源归属校验。
2. 没有多租户隔离和生产级访问控制。
3. 使用 SQLite 和本地文件系统，缺少生产级备份、恢复、并发控制和对象存储策略。
4. 文件上传缺少病毒扫描、沙箱隔离和内容安全扫描。
5. 没有 TLS、反向代理、安全 header、限流、WAF 和公网部署配置。
6. 没有完整审计日志、可观测性、告警和故障恢复流程。
7. 文献 metadata 没有真实数据库或 DOI 联网核验。
8. Reviewer 和 Claim Alignment 仍是规则系统，不是正式科研审稿或合规审查。
9. Mock fallback 是本地 demo 友好设计，不是生产数据一致性策略。
10. 没有生产级 secrets 管理和配置治理。

结论：v0.3 可用于本地 demo、研发验收、可信链路原型和 v0.4 增量开发基线，不得直接开放公网或承载真实投稿工作流。

## 12. v0.4 推荐方向

v0.4 推荐方向收敛为以下七项。登录、多租户、PostgreSQL、Celery、LangGraph 不作为 v0.4 必做项，放到 v0.5 或 v1.0 再评估。

### A. Reviewer sentence issue 精确修订 diff

目标：

- 在 `sentence_issues` 中增加可读的 before / after 修订建议。
- 对 overclaim、missing evidence、needs_claim_alignment 生成最小改写建议。
- 保持 Reviewer 只指出风险和建议，不替用户伪造事实。

保护边界：

- 不得自动把无证据句子改成 supported。
- 不得生成 p 值、因果关系或真实引用。

### B. Literature metadata 变更历史

目标：

- 为 Literature Metadata Editor 增加 metadata change history。
- 记录谁改了什么字段、旧值、新值、时间和来源。
- v0.4 可先使用本地 JSON 变更历史，不必引入数据库迁移。

保护边界：

- 不得自动核验 DOI。
- 不得自动把 placeholder 改成 verified。

### C. PDF 页级质量报告和 OCR fallback 预留

目标：

- 将 PDF quality 从文件级扩展到页级。
- 记录每页 char_count、empty flag、warning、quality signal。
- 为 OCR fallback 预留结构字段，但 v0.4 不要求真正接入 OCR 引擎。

保护边界：

- OCR 未实际执行时不得标记为已 OCR。
- 低质量页不得被当作可靠全文来源。

### D. Analysis provenance 参数、脚本版本、随机种子

目标：

- 扩展 `analysis/analysis_provenance.json`。
- 记录分析参数、脚本或函数版本、随机种子、输入文件 hash、输出文件 hash。
- 明确 demo data 和 limitation。

保护边界：

- 不得伪造统计检验。
- 不得把描述性分析写成显著性或因果结论。

### E. 真实后端 Playwright E2E

目标：

- 在现有 mock fallback E2E 之外，增加真实后端 demo workflow E2E。
- 覆盖 seed demo、run workflow、打开新增面板、读取真实 API 数据。
- 保持 E2E 不依赖公网、真实 LLM API 或外部服务。

保护边界：

- E2E 失败不得被静默跳过。
- mock fallback 和真实后端 E2E 要分开命名。

### F. 最小审计日志

目标：

- 记录关键本地操作：
  - run workflow
  - run step
  - literature metadata PATCH
  - upload literature/data
- v0.4 可先写入项目本地 JSONL 文件。

保护边界：

- 不记录 API key、secret 或敏感绝对路径。
- 不把审计日志当作权限系统。

### G. 任务运行历史

目标：

- 记录每次 workflow / step 的运行历史。
- 包含 start_time、end_time、status、step、outputs、errors。
- 前端可展示最近运行记录。

保护边界：

- 不引入复杂队列。
- 不把任务历史当作 Celery 或生产任务系统。
- 不破坏当前同步 workflow demo 能力。
