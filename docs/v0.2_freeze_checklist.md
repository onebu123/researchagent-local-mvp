# ResearchAgent v0.2 冻结清单

冻结日期：2026-06-05

冻结状态：v0.2 已通过验收，进入版本冻结。冻结后不再继续开发 v0.2 功能；后续功能、重构和架构演进必须进入 v0.3 范围。

## 1. v0.2 已完成能力

### 1.1 PDF 文献解析

- 支持上传或 seed PDF 后保留原始 PDF。
- 生成解析文本：
  - `projects/demo_project/literature/parsed/demo_pdf_literature.txt`
- 生成解析 metadata：
  - `projects/demo_project/literature/parsed/demo_pdf_literature.metadata.json`
- PyMuPDF 不可用时可 graceful fallback 到基础 PDF literal text parser。
- PDF 解析失败时不删除原始文件，错误写入 metadata warnings。

### 1.2 文献 metadata

- 生成文献索引：
  - `projects/demo_project/literature/literature_index.json`
- 每条记录包含：
  - `literature_id`
  - `source_file`
  - `title`
  - `authors`
  - `year`
  - `doi`
  - `source_type`
  - `parsed_text_file`
  - `metadata_status`
  - `human_verified`
- demo 文献明确标记为 `placeholder`，不会伪装为 verified reference。

### 1.3 Evidence 多 claim

- `provenance/evidence.json` 已从 v0.1 单条 claim 扩展为至少 3 条 claim。
- 当前 demo 包含：
  - `claim_001`：analysis_summary claim
  - `claim_002`：figure claim
  - `claim_003`：manuscript_results claim
- Results claim 绑定 analysis 或 figure 文件。
- Evidence Checklist 中列出 `claim_id`。

### 1.4 Figure provenance

- `figures/figure_provenance.json` 至少包含 2 条图表记录。
- 每条记录包含：
  - `figure_id`
  - `title`
  - `figure_type`
  - `source_data`
  - `analysis_file`
  - `script_or_function`
  - `output_files`
  - `is_ai_generated=false`
  - `is_experimental_result=true`
  - `created_at`
  - `data_hash`
  - `warnings`
- `data_hash` 使用 source CSV SHA256。
- source data 不存在时不伪造图表。

### 1.5 Manuscript 增强

- `manuscript/draft.md` 包含 Evidence Checklist。
- Evidence Checklist 中出现 `claim_id`。
- Results 仅基于：
  - `analysis/result_summary.json`
  - `figures/figure_provenance.json`
- References 分为：
  - `Placeholder literature records`
  - `Verified references`
- placeholder 文献明确提示需要人工核验。
- 不生成伪造 DOI、作者、年份、期刊、页码、p 值或统计显著性结论。

### 1.6 Reviewer 增强

- `reviews/review_report.json` 包含：
  - `overall_decision`
  - `major_issues`
  - `minor_issues`
  - `citation_issues`
  - `evidence_issues`
  - `figure_issues`
  - `statistical_issues`
  - `overclaims`
  - `consistency_checks`
  - `recommended_revisions`
- Reviewer 会检查：
  - Evidence Checklist 是否存在。
  - checklist claim_id 是否存在于 evidence.json。
  - 强结论词和统计证据是否匹配。
  - figure provenance 是否完整。
  - row_count、column_count 是否与 manuscript 一致。
  - placeholder literature 是否进入 citation issues。
- 当前 demo 因 placeholder 文献，`overall_decision=major_revision`，符合冻结预期。

### 1.7 后端 API

新增 v0.2 API：

- `GET /api/projects/{project_id}/evidence`
- `GET /api/projects/{project_id}/figures/provenance`
- `GET /api/projects/{project_id}/outputs/{output_id}/file`

文件缺失返回 404；项目文件读取经过路径边界保护。

### 1.8 前端详情能力

- RecentOutputs 点击输出后打开详情 drawer。
- 支持预览：
  - Markdown
  - JSON
  - TXT
  - CSV 前 20 行
  - SVG
  - PNG
- 新增：
  - `apps/web/components/EvidencePanel.tsx`
  - `apps/web/components/FigureProvenancePanel.tsx`
  - `apps/web/components/OutputDetailDrawer.tsx`
- Dashboard 增加：
  - 查看证据链
  - 查看图表来源
- 后端不可用时仍可 mock 渲染。

## 4. v0.2 已知限制

- PDF 解析只是基础能力，不保证复杂 PDF、扫描 PDF、双栏论文、表格、公式和图片注释的高质量抽取。
- PyMuPDF 不可用时 fallback 能力有限，只适合 demo/简单 PDF。
- 文献 metadata 仍以 placeholder/extracted 结构为主，不联网核验 DOI、作者、年份、期刊或页码。
- `human_verified` 只作为 JSON 字段存在，尚无前端人工核验工作流。
- Evidence claim 由规则生成，不做 sentence-level 对齐。
- Reviewer 是规则检查器，不是正式审稿系统。
- Reviewer 能检测明显 overclaim，但不能理解所有学术语义风险。
- Analysis 只做描述性统计，不生成真实统计检验、p 值、置信区间或因果推断。
- Figure provenance 有 hash 和 output files，但没有完整 analysis provenance、脚本版本锁定或运行环境快照。
- 前端详情为 drawer 级最小实现，不是完整输出管理系统。
- SQLite 和本地文件存储只适合本地 demo，不适合并发、多用户和公网生产。
- Mock fallback 仍是核心运行方式之一，不能代表真实 LLM 质量。

## 5. v0.2 为什么不能用于公网生产

v0.2 是本地可信草稿系统 baseline，不是公网生产系统。原因如下：

1. 无用户登录、认证、授权和多租户隔离。
2. 无生产级项目权限、文件访问权限和成员体系。
3. 使用 SQLite 与本地文件系统，缺少生产级迁移、备份、恢复、并发控制和对象存储。
4. PDF 上传缺少病毒扫描、沙箱隔离、内容安全扫描和异步隔离处理。
5. 没有公网部署配置、TLS、反向代理、安全 header、限流和 WAF。
6. 没有完整审计日志、可观测性、告警和故障恢复流程。
7. 没有正式 secrets 管理和生产配置管理。
8. Reviewer 和 evidence 仍是规则链路，不能替代专家审查或合规审查。
9. 文献 metadata 未连接真实数据库或人工审核流程，不能作为投稿引用依据。
10. 前端 mock fallback 是 demo 友好设计，不是生产数据一致性策略。

结论：v0.2 只能用于本地 demo、研发验收、可信链路原型验证和 v0.3 需求准备，不得直接开放公网或承载真实用户/真实投稿工作流。

## 6. v0.2 与 v0.1 的主要差异

| 维度 | v0.1 | v0.2 |

| API | outputs API 为主 | 增加 evidence、figure provenance、output file API |

## 7. v0.3 开发前必须保护的边界

v0.3 开发前必须保护以下 v0.2 baseline：

1. `python scripts/validate_v01.py` 必须继续通过。
2. `python scripts/validate_v02.py` 必须继续通过，除非先更新验收文档并明确迁移理由。
3. 不得删除或破坏：
   - `literature/literature_index.json`
   - `literature/parsed/*.txt`
   - `literature/parsed/*.metadata.json`
   - `analysis/result_summary.json`
   - `figures/figure_provenance.json`
   - `provenance/evidence.json`
   - `manuscript/draft.md`
   - `reviews/review_report.json`
4. 不得把 placeholder 文献标记为 verified。
5. 不得自动生成伪造 DOI、作者、年份、期刊、页码。
6. 不得伪造 p 值、统计显著性、因果结论或真实实验结论。
7. 不得把 AI 生成图伪装成实验图。
8. `figure_provenance.json` 必须继续保留 `is_ai_generated=false`、`is_experimental_result=true`、`source_data`、`output_files`、`data_hash`。
9. Evidence claim 必须继续有稳定 `claim_id`。
10. Manuscript Evidence Checklist 必须继续列出 `claim_id`。
11. Reviewer 必须继续能将 placeholder literature 写入 `citation_issues`。
12. 后端缺文件 API 必须返回清晰 404，不得静默返回空成功。
13. 上传和输出文件读取必须继续保留路径越界保护。
14. 无 API key 环境必须继续可运行 mock demo。
15. 前端后端不可用时必须继续可 mock 渲染。
16. v0.3 不得以“大改架构”为由一次性替换整个 v0.2 workflow。

## 8. v0.3 推荐目标

### 8.1 Post-Manuscript Claim Alignment

目标：在 manuscript 生成后，对正文句子和 `evidence.json` claim 做二次对齐。

建议验收：

- 能从 `draft.md` 提取 Results/Discussion 关键句。
- 每个关键句关联 claim_id 或标记为 `needs_claim_alignment`。
- Reviewer 能报告 manuscript 中未绑定 claim 的句子。
- 不改变 v0.2 evidence 基础字段，只扩展对齐字段。

### 8.2 Reviewer sentence-level issue 定位

目标：Reviewer 不只给全局 issue，还能定位到 manuscript 句子或段落。

建议验收：

- `review_report.json` 增加 sentence-level issue 列表。
- 每条 issue 至少包含：
  - `issue_id`
  - `section`
  - `sentence`
  - `issue_type`
  - `severity`
  - `related_claim_id`
  - `suggested_revision`
- 前端可以查看 issue 对应句子。

### 8.3 Literature Metadata Editor

目标：提供最小人工编辑入口，让 placeholder metadata 能被人工补全和核验。

建议验收：

- 前端可查看和编辑 title、authors、year、doi、source_type、metadata_status、human_verified。
- 后端保存前校验字段类型和 DOI 格式。
- Verified references 只能来自 `human_verified=true` 且 metadata_status 为 verified 的记录。
- 修改 metadata 后 Reviewer decision 可变化，但不得自动伪造字段。

### 8.4 PDF Parse Quality Report

目标：评估 PDF 解析质量，避免把低质量文本当成可靠文献输入。

建议验收：

- 每个 PDF metadata 增加 parse quality 指标：
  - text_length
  - page_count
  - empty_page_count
  - extraction_method
  - warning_count
  - quality_score
- 低质量解析进入 Reviewer `metadata_issues` 或 `citation_issues`。
- 前端能展示 parse_status 和 quality_score。

### 8.5 Analysis Provenance

目标：把 analysis 从 result summary 扩展为可追溯分析运行记录。

建议验收：

- 新增 `analysis/analysis_provenance.json`。
- 记录：
  - input data file
  - data hash
  - analysis function
  - generated files
  - created_at
  - library/runtime version summary
  - warnings
- Evidence analysis claim 必须能绑定 analysis provenance。

### 8.6 Playwright E2E

目标：增加真实浏览器端到端测试，覆盖可信链路前端入口。

建议验收：

- E2E 能启动或连接本地后端和前端。
- 覆盖：
  - dashboard 加载 demo_project。
  - RecentOutputs 打开 draft.md。
  - 打开 EvidencePanel 并看到 claim_001/claim_002/claim_003。
  - 打开 FigureProvenancePanel 并看到 `data_hash`。
  - 后端不可用时 mock fallback 可渲染。
- E2E 不依赖公网和 API key。

## 9. 冻结后变更规则

- v0.2 冻结后，只允许文档更正、测试说明更正和明确 bugfix。
- bugfix 必须说明是否影响 v0.2 freeze baseline。
- 任何新增功能必须进入 v0.3 分支或 v0.3 文档。
- 修改 JSON schema 前必须同步更新：
  - `docs/v0.2_freeze_checklist.md`
  - `docs/v0.2_acceptance_report.md`
  - `scripts/validate_v02.py`
  - 相关 pytest
  - 前端类型定义
- 不得在未更新验收标准的情况下破坏 v0.2 既有命令。
